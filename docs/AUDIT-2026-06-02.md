## Severity scale

## Layer 1 — Toolchain

**Solid**
- TypeScript strict mode on
- `server-only` package installed and used as a structural boundary
- `npm run check` chains typecheck + lint
- PowerShell setup-check script with color output
- Dev port (`4321`) avoids common collisions
- Demo-mode fallback works without any env vars

**Flags**
- 🔴 **No test suite exists.** For a constitutionally-strict product, zero tests means structural invariants (gates, immutability, RLS) are not regression-protected. The first time we change the gate trigger, we have no automated guard that the change still rejects under-evidenced problems.
- 🟠 **No env validation.** A typo in `.env.local` (e.g. `DEEPSEAK_API_KEY`) fails at LLM call time with confusing errors instead of startup with a clear message. Zod schema at `process` boundary would fix.
- 🟠 **No CI.** No `.github/workflows`. Anyone can push code that breaks typecheck or lint without warning.
- 🟠 **`eslint-config-next: 15.3.2`** vs `next: ^16.2.6` — version mismatch may miss lint rules. Upgrade to `eslint-config-next@^16`.
- 🟡 `target: ES2017` is conservative for Node 24. Upgrade to ES2022 to stop downleveling modern features.
- 🟡 No `noUncheckedIndexedAccess` in tsconfig — `arr[i]` typed `T` instead of `T | undefined`. Has already burned me once.
- 🟡 `.next/dev/types/**/*.ts` is in tsconfig include (Next re-adds it). Has bitten us once with stale type files; we work around by deleting the dir.
- 🟡 Prettier expected by `.vscode/settings.json` but not in dependencies.
- 🟡 `next.config.ts` is empty — no security headers, no `output: 'standalone'`, no image config.

## Layer 2 — Type / boundary hygiene

**Solid**
- 9 files marked `import "server-only"` — exactly the LLM/brain/auth-helper boundary
- 20 files marked `"use client"` — the dashboard pages, layouts, hooks
- Zero `any`, `as any`, `@ts-ignore`, `@ts-expect-error` across the entire `src/`
- Diagnosis index narrowed to client-safe re-exports after the Anthropic-in-browser bug

**Flags**
- 🟠 **No automated guard on the boundary.** A new server-only module without the marker only fails at first browser import. A lint rule (or test) would catch immediately. We already fell into this hole once.
- 🟡 `src/lib/diagnosis/closeLoop.ts` uses the **browser** Supabase client but lives next to `outsideView.ts` / `rippleTrace.ts` which are server-only. The naming makes the boundary ambiguous. Possibly worth splitting into `closeLoop.client.ts` or similar.
- 🟡 No verification that client bundles don't contain server code (Next's RSC boundary handles this implicitly; we could be explicit with a build-step assertion).

## Layer 3 — Schema (migrations 0001 → 0008)

**Solid**
- 8 migrations, 57 RLS/function/trigger statements, 43 idempotency guards
- Append-only enforced via SQL rules on `events`, `signals`, `problem_signals`, `brain_evolution_events`
- Immutability triggers on `decision_dialogues` (user-authored fields) and `resolutions` (action/reasoning/decided_at)
- Understanding Gate enforced at DB layer (cannot be bypassed by app code)
- `record_brain_learning()` is the only sanctioned brain mutation path — bumps version + appends audit in one transaction
- `close_problem()` atomically inserts resolution + marks problem resolved + emits new event

**Flags**
- 🔴 **Migration 0008 is unrun and unused.** Team invitations schema exists but no API or UI consumes it. Either wire it up or note it as deferred.
- 🟠 **No migration runner.** Plain SQL files — running them out of order or skipping one isn't prevented. No `npm run db:migrate` integration. Each migration must be pasted into the Supabase SQL editor manually.
- 🟠 **No down migrations.** Can't reverse cleanly. If a customer hits a bad migration we have nothing.
- 🟠 **Signal derivation template substitution is naive.** `regexp_replace` with hardcoded payload key lookup only handles `task_id` and `meeting_id`. Other event kinds emit signals with `'unknown'` source. Fragile.
- 🟡 **Free-text event/signal kinds.** No enum or lookup table — a typo in app code creates orphan rows that no derivation rule matches. Should be a `kinds` registry table.
- 🟡 **`signals_no_update`/`_no_delete` rules use `do instead nothing`.** Silently swallows the operation. Should `raise exception` so the violation is loud.
- 🟡 **No FK indexes** on most foreign keys. Postgres doesn't auto-index them; this will bite at scale.
- 🟡 **No event versioning.** As `events.payload` shape evolves, old events keep the old shape with no upgrade path. The §3.1 archaeology will eventually need this.
- 🟡 `security definer` functions don't all set `search_path` explicitly. `accept_invitation` does; `create_empty_brain_for_company` does not. Mild security smell.
- 🟢 `record_brain_learning` accepts arbitrary JSON blobs with no schema validation — relies on the caller (currently only `learn.ts`) to send well-formed data.

## Layer 4 — RLS policies

**Solid**
- Every table has RLS enabled
- Standard pattern: `using (company_id = auth_company_id()) with check (company_id = auth_company_id())`
- Helper function `auth_company_id()` is `security definer` for safe profile lookup
- Cross-table policies (e.g. `problem_signals` scoped through parent problem) are correctly composed

**Flags**
- 🟠 **No RLS test coverage.** Per Rule 1.7, the RLS is what guarantees company isolation — but we have no test that proves company A cannot see company B's tasks. This is the single most security-critical invariant in the product and it is not regression-protected.
- 🟡 **`profiles` table got a company-wide SELECT policy in migration 0008** ("company members - select profiles") — fine, but the migration is unrun so it's not active yet. Documentation should reflect that the policy depends on 0008.
- 🟡 No deny-by-default test for unauthenticated access — should verify that with no JWT, every table returns empty.
- 🟢 No `service_role` access pattern documented (server-side mutations that need to bypass RLS, e.g. seed routes).

## Layer 5 — Data fetchers

**Solid**
- All four production fetchers (`tasks.ts`, `signals.ts`, `problems.ts`, `resolutions.ts`) return a `mode` discriminator: `'demo-fixtures' | 'live-empty' | 'live-data'`
- Callers decide rendering based on `mode` — no silent mock fallback in live mode
- Browser-client-safe (no `server-only` markers; client pages can import freely)

**Flags**
- 🟡 **`fetchProblems` and `fetchResolutions` don't have a demo-fixtures branch** — they return `mode: 'demo-unavailable'` instead, which forces an "live mode required" banner. Inconsistent with `fetchTasks` / `fetchSignals` which DO have mock fixtures. Either make it consistent (mock fixtures everywhere) or document why these two are different.
- 🟡 No caching, no SWR/React Query. Every page fetches on mount. Most pages re-fetch on user interaction. Network thrash will be visible at scale.
- 🟢 Fetchers don't share error handling — each catches `error || !data` and returns empty. A network blip silently looks like "no data."

## Layer 6 — API routes

**Solid**
- 22 routes total. Auth checked via `getCurrentCompanyId()` helper in 19 of them.
- Constitutional refusals return HTTP 400 with explicit constitutional reasons (e.g. "your diagnosis is required before the System can respond")
- Gate violations from the DB trigger return 422 (not 500) — distinguishes constraint-from-error
- Deprecated routes return 410 Gone with pointer to the replacement
- Method restriction enforced (e.g. `/api/resolutions` only allows PATCH because resolutions are only created via `close_problem` RPC)
- Soft-delete path on tasks (sets `deleted_at`, doesn't DROP)

**Flags**
- 🔴 **Legacy `/api/ai/analyze`, `/api/ai/finance`, `/api/ai/marketing` routes still exist** and call `analyzeOperations`/`analyzeFinance`/`analyzeMarketing` — which still emit the OLD §3.3-violating output shape (`healthScore: 0-100, diagnosis: "..."`, etc.). Even though no UI calls them now, the routes are publicly accessible and a customer or partner could call them and get overtake-flavor responses.
- 🟠 **No request-body schema validation.** Each route does ad-hoc `if (typeof x !== 'string')` checks. Zod or similar would centralize and harden.
- 🟠 `/api/seed` writes `mockTasks` / `mockTeamMembers` / `mockDecisionHistory` into a real company. This was a bootstrap tool but per AMD-003 and §3.4, **populating a live company with mock data violates the honesty contract** ("a system that behaved identically for every customer on install would be claiming understanding it cannot have — a lie"). Should be removed or renamed to `/api/dev-seed` and explicitly dev-only.
- 🟡 No rate limiting on any route. Every AI route is unauthenticated-callable (no auth check on `/api/ai/briefing`) — could be abused.
- 🟡 No structured logging. Errors return generic 500s; nothing tells the operator what failed.
- 🟢 No OpenAPI / schema export. Hard for external integrations.

## Layer 7 — LLM provider abstraction

**Solid**
- `chooseProvider()` selects by env override or auto-detects
- DeepSeek primary per AMD-003
- Anthropic kept as a configurable alternate (single-provider-failure defense)
- `LlmCallArgs` + `LlmResult` are small, clean types
- `server-only` enforced on all provider files

**Flags**
- 🟠 **No retry / timeout logic.** A flaky DeepSeek call hangs forever or fails permanently. Should have `AbortController` with timeout + exponential-backoff retry on transient errors.
- 🟠 **No model fallback.** If DeepSeek's `deepseek-chat` is rate-limited, the call dies. Could degrade to a smaller/cheaper variant.
- 🟡 **No token accounting.** We don't track tokens consumed per company, so we can't bill or rate-limit by usage.
- 🟡 **No structured error type.** Every provider throws `Error`. Caller can't distinguish auth failure from rate-limit from network from server-error.
- 🟢 DeepSeek client uses raw `fetch`; could use the official SDK for streaming/usage data if/when added.

## Layer 8 — Brain composer + control gate

**Solid**
- `runBrainCall()` is the single entry point for company-aware calls
- §3.4 control gate enforced — calls return `suppressed: true` during Month 1
- Brain composer appends a "discipline reminder" to every prompt (the AMD-003 echo-chamber defense)
- Manual unlock requires ≥20-char reason, recorded in audit trail
- `record_brain_learning()` RPC is atomic (version bump + audit append)
- Learning cycle refuses to run when there's no validated evidence

**Flags**
- 🟠 **`auto-unlock` at day 30 is silent.** No event, no notification, no record. Per §3.6 the user should see "AI guidance just unlocked — here's what changed."
- 🟠 **Brain composer doesn't truncate.** If a company has hundreds of patterns, the system prompt blows past token limits. We cap `known_patterns` at 20 in the composer but not `validated_methods` / `disabled_suggestions` / `addendum`.
- 🟡 **`unlockControlGate` audit record uses `confidence: 'low'`** — fine but the reason field of the audit shows the user's reason, not the *type* of override. A future operator reviewing audits won't be able to tell at a glance "this was an early-unlock override" vs "this was something else with confidence:low."
- 🟡 The learning cycle hits the LLM with a fixed `DISTILL_SYSTEM_PROMPT` that does NOT route through the brain — by design (system-level call), but worth documenting that distinction in code.
- 🟢 `loadBrain()` throws if brain row missing — relies on the `companies_create_brain` trigger from 0007 having fired. If a company exists without a brain row (manual SQL insert, etc.), all LLM calls fail.

## Layer 9 — Diagnosis engine

**Solid**
- 7 steps clearly defined and each has an explicit `canAdvance` rule
- Retrospective pattern detection is pure (no LLM dependency)
- Understanding Gate evaluator mirrors the DB trigger (documented as "if mirror and trigger disagree, trigger wins")
- Outside-view + ripple-trace go through `runBrainCall` when company is present
- Close-loop atomicity enforced at SQL layer via `close_problem()` RPC

**Flags**
- 🟠 **No persistence of a diagnosis run.** The user walks 7 steps in-memory; if they refresh, state is lost. Should persist `diagnosis_runs` as their own DB rows (with append-only step transitions).
- 🟠 **No "back-link from problem to diagnosis run."** A diagnosis that produces a resolution doesn't reference which `diagnosis_run` produced it. The chain `problem → diagnosis_run → resolution` is implied but not stored.
- 🟡 Outside-view function silently returns `[]` when JSON parse fails. Should distinguish "no readings generated" from "parse error" upstream.
- 🟡 `evaluateUnderstandingGate` defaults match the DB defaults — but if the DB `problem_thresholds` row is changed per-kind, the client mirror doesn't know about it. Should fetch the actual threshold for the problem's kind.

## Layer 13 — Onboarding + auth

**Solid**
- 4-step onboarding flow with progress indicator
- Sign-in/sign-up toggle on `/login`
- Demo-mode passthrough (no Supabase) works end-to-end
- Middleware refreshes session and gates `/dashboard`
- Onboarding writes `companies` + `profiles` atomically (well, sequentially with explicit error handling)

**Flags**
- 🟠 **Onboarding doesn't seed the brain.** It creates the company; the trigger creates the brain row; but neither emits a `company.created` event or records anything for the brain to start with. The brain begins truly empty (which is constitutionally correct) but the user has no signal that the chain has started.
- 🟠 **No password reset.** Sign-up only.
- 🟠 **No email verification flow** in the app — users must toggle "Confirm email" off in Supabase manually (documented in `LOCAL_DEV.md`). Acceptable for now but not for paid customers.
- 🟡 **No "what to do first" tour** after onboarding. User lands in a dashboard with the Quickstart panel suggesting "create your first task" but no guided walkthrough.
- 🟡 **Onboarding's "goals" selection step doesn't persist anywhere.** User picks goals; the data is dropped on submit. Should write to `companies.goals` or similar so the brain can use it later.
- 🟢 Landing page (`src/app/page.tsx`) still uses overtake-flavor copy ("AI Executive Briefing", "Team Intelligence") inconsistent with the current product. Pre-constitution language.

## Cross-cutting findings (don't belong to a single layer)

- 🔴 **Mock data is still importable from production code paths** even where production no longer uses it. `mock-data.ts` exports `mockCompany`, `mockTasks`, etc. and the Settings page (Layer 12) + landing page (Layer 13) still consume them. As long as those exports exist, the §3.4 "no day-one behavior" rule has a backdoor.
- 🔴 **Per §1.7's own "empty flags is suspicious" rule, no layer above produced zero flags.** That itself is evidence the audit was honest — but it also means every layer has *something* that could fail. This is the realistic state of a working product, but it means we should plan for incident response.
- 🟠 **No `audit` event type.** This audit itself should be recorded as `audit:layer-N` events per §1.7's own rule #4. The discipline applies to itself.
- 🟠 **No production logging/observability.** When a customer hits an error, we have no trail.

   immutability discipline applied to the audit record itself.
